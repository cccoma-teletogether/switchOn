# 개발 문서

## 1. 개요

스위치온 다이어트 매니저는 브라우저에서 바로 실행하는 정적 웹앱입니다.

- 진입점: `index.html`
- 화면 스타일: `style.css`
- 상태·렌더링·이벤트 처리: `app.js`
- 참고 이미지: `assets/`
- 외부 서버/API: 없음
- 저장소: 브라우저 `localStorage`

현재 별도의 `package.json`, 번들러, 테스트 러너는 없습니다. 따라서 파일을 정적 파일 서버로 제공하거나 브라우저에서 `index.html`을 열어 확인할 수 있습니다. 개발 시에는 정적 서버 사용을 권장합니다.

```powershell
# 저장소 루트에서 실행 예시
py -m http.server 8000
# 브라우저에서 http://localhost:8000 접속
```

## 2. 화면 구성

`index.html`은 다음 순서의 단일 대시보드로 구성됩니다.

1. 프로그램 주차·기간·상태 요약
2. 월간 캘린더와 측정일/단식일 표시
3. 다음 주차 진행 판정
4. 체성분 그래프
5. 날짜별 측정 기록
6. 주차별 진행 기록
7. 측정 기록, 시작일, 식단 가이드, 이미지 확대용 `dialog`

## 3. 상태 모델

`app.js`의 `state`가 화면의 단일 상태 원천입니다. 변경 후 `persist()`가 호출되어 `localStorage`에 저장됩니다.

주요 필드:

| 필드 | 설명 |
|---|---|
| `startDate` | 프로그램 시작일. 주차 계산 기준 |
| `height` | BMI 계산용 키(cm) |
| `stage` | 현재 주차 |
| `repeat` | 현재 주차 반복 횟수 |
| `records` | 날짜별 체중·근육량·체지방 기록 배열 |
| `fastingDays` | 단식일로 지정한 `YYYY-MM-DD` 배열 |
| `decisionChecks` | 운동 수행, 피로, 단백질 섭취의 사용자 자기점검 |
| `chart`, `chartRange`, `chartWeek` | 그래프 선택 상태 |
| `selected` | 캘린더에서 선택한 날짜 |

측정 기록의 대표 형태는 다음과 같습니다.

```json
{
  "date": "2026-11-09",
  "weight": 67.8,
  "muscle": 28.1,
  "fat": 17.4,
  "fatPercent": 25.7,
  "note": "운동 후 컨디션 양호"
}
```

체지방 입력은 화면에서 체지방률(%)로 받고, 체지방량은 `체중 × 체지방률 ÷ 100`으로 계산합니다. 이전 데이터에 체지방량만 있는 경우에는 기존 `fat` 값을 사용할 수 있도록 호환 처리합니다.

## 4. 주요 동작

### 주차 계산

`startDate`부터 7일 단위로 주차를 계산합니다. 시작일을 변경하면 캘린더의 주차 표시, 주차별 기록, 그래프 비교 구간이 함께 바뀝니다. 초기 구현의 기본 시작일은 `2026-10-26`입니다.

### 체성분 그래프

- 지표: 근육량, 체지방량, 체중
- 비교 기준: 초기 기준 대비, 주차별, 최근 1주일
- 초기 기준: 근육량·체지방량은 `initial` 상수, 체중은 시작 후 첫 주 기록을 우선 사용
- 측정값이 2개 이상이면 선형 추세선을 표시
- 측정 데이터가 없는 구간은 안내 문구를 표시

### 다음 주차 판정

판정은 단일 수치가 아니라 다음 요소를 조합합니다.

- 초기/시작 기준 대비 체중, 체지방률, 체지방량 변화
- 최근 7일과 직전 7일의 평균 변화
- 근육량의 최근 방향과 저점 이후 회복 여부
- 운동 수행력, 피로, 단백질 섭취 자기점검

결과는 적극 진행 추천, 진행 가능, 조건부 통과, 전체 추세 확인, 연장 검토 등의 상태로 표시됩니다. ±0.5kg 같은 값은 앱 안의 참고 로직이며 의료적 진단이나 공식 판정 기준이 아닙니다.

### 데이터 백업·복원

- 저장하기: 현재 주요 상태를 JSON 파일로 다운로드
- 불러오기: `records` 배열이 있는 JSON만 허용하고 화면을 새로고침
- 초기화: `switchon-app-v2` 키를 삭제하고 앱을 다시 로드

백업 파일에는 `version`, `exportedAt`, 시작일, 키, 주차, 기록, 단식일, 자기점검이 포함됩니다. 사용자가 직접 편집한 JSON은 형식 오류나 비정상 수치가 발생할 수 있으므로 가져오기 전 백업을 권장합니다.

## 5. 개발 규칙

- 기존 기능을 수정할 때 `state` 변경 → `persist()` → 관련 렌더 함수 호출 순서를 유지합니다.
- DOM 선택자는 `index.html`의 `id`·`data-*` 속성과 함께 변경합니다.
- 식단·판정 문구는 코드에 직접 포함되어 있으므로 문구 수정 시 주차별 가이드와 판정 표를 함께 확인합니다.
- 사용자 데이터는 서버로 전송하지 않습니다. 개인정보·건강정보를 추가 저장할 때는 저장 범위와 삭제 방법을 먼저 정의합니다.
- 외부 참고 링크나 이미지의 출처가 바뀌어도 앱이 깨지지 않도록 이미지 파일은 `assets/`에 포함합니다.

## 6. 수동 QA 체크리스트

- 첫 방문 시 기록 없음 상태와 데모 데이터 초기화가 정상인지 확인
- 오늘 기록 추가·수정 후 캘린더, 그래프, 기록 표, 주차 판정이 함께 갱신되는지 확인
- 체중·체지방률 입력 시 자동 체지방량 계산이 맞는지 확인
- 캘린더 월 이동, 오늘 이동, 시작일 변경을 확인
- 단식일 지정/해제가 새로고침 후에도 유지되는지 확인
- 그래프의 지표·비교 범위·주차 선택을 각각 확인
- 자기점검 3개 항목 변경 시 판정 상태와 경고 문구가 바뀌는지 확인
- 현재 주차 반복 및 다음 주차 진행 후 `stage`·`repeat`가 올바른지 확인
- JSON 저장 후 저장 파일을 불러와 동일한 데이터가 복원되는지 확인
- 모바일 폭에서 표, 대화상자, 그래프, 이미지 확대가 사용 가능한지 확인
- 이미지 파일이 없어도 나머지 앱 화면이 중단되지 않는지 확인

## 7. 알려진 제한사항

- 서버 동기화, 계정, 다중 기기 동기화가 없습니다.
- 브라우저 저장소를 삭제하면 데이터가 사라집니다. JSON 백업이 필요합니다.
- 입력값의 생리학적 타당성, 측정 조건, 단위는 충분히 검증하지 않습니다.
- 현재 코드에는 자동화된 테스트와 린트 설정이 없습니다.
- 기획 콘텐츠와 건강 관련 표현은 참고 자료 기반이며 의료진의 진단을 대체하지 않습니다.

## 8. 향후 기술 개선 후보

1. 입력값 스키마 검증과 비정상 범위 경고 추가

3. `state`·렌더링·저장소 어댑터 분리
4. JSON 마이그레이션 버전 관리
5. Playwright 또는 브라우저 기반 회귀 테스트 도입
6. 접근성 점검과 키보드 탐색 자동 테스트
